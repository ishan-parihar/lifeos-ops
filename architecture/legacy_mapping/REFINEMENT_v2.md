## The Core Shift

The previous framings (A/B/C/D) treated LifeOS as a static structure — buckets holding DBs. The user's correction exposes the flaw: **a consciousness-prosthetic isn't a structure, it's a PROCESS.** The structure only exists to keep the process flowing.

Three shifts follow:

1. **From containers to processes.** The 3 engines (Definition / Action / Context) aren't buckets holding DBs — they're processes kept running by the synthesis pipeline flowing through the user's trajectory.

2. **From tool to symbiont.** LifeOS isn't a tool the user picks up. It's a prosthetic extension of the user's cognition. User + LifeOS form a coupled system — a symbiosis.

3. **From logs-as-buckets to perception-as-system.** The 6 logs aren't 6 buckets inside an engine. They're ONE perception system — the input layer that feeds the entire prosthetic.

## How the 3 Engines Operationalize Themselves

The user's key correction: engines aren't static. They **operationalize themselves** through two flows.

### Flow 1: Synthesis flowing IN (the bloodstream)

The synthesis pipeline doesn't just produce insights — it **regenerates the engines**:

| Synthesis output | → Definition Engine | → Action Engine | → Context Engine |
|------------------|--------------------|-----------------|------------------|
| Opportunities-and-Strengths (+) | Reaffirms Values/Vision (what's working is who I am) | Capitalizes via new Projects (double down on strengths) | Deepens engagement with high-value People/Communities |
| Directives-and-Risks (−) | Revises Values/Vision (what's breaking reveals what matters) | Spawns corrective Projects/Tasks (fix the trajectory) | Restructures engagement (exit low-value relationships) |
| Notes-Management (raw) | Feeds long-term trait condensation into Stats | Informs goal revision | Informs context reassessment |

Without synthesis flowing in, the engines freeze. Values never get revised. Goals never adapt. Context never updates. The engine "dies" — it becomes a static bucket instead of a living process.

### Flow 2: Trajectory flowing THROUGH (the spine)

The user's real-life trajectory is the temporal arc the engines flow along:

| Trajectory movement | → Definition Engine | → Action Engine | → Context Engine |
|--------------------|--------------------|-----------------|------------------|
| User lives (generates logs) | Stats updates (new traits condense) | Tasks complete, Projects advance | Context shifts (new interactions, transactions) |
| User grows (developmental shift) | Vision evolves (new altitude) | Goals decompose at higher level | New People/Communities become relevant |
| User regresses (crisis, setback) | Values tested (which hold?) | Goals pause/revise | Support network activates |

Without trajectory flowing through, the engines have nothing to process. They're empty processes — running but meaningless.

### The intersection: where engines live

An engine is alive **only at the intersection** of synthesis flowing in + trajectory flowing through. This is why the engines "operationalize themselves" — they don't exist as static structures, they exist as **processes at the crossing point of two flows**.

## The User ⇌ LifeOS Coupling

The user isn't "using" LifeOS. They're **coupled** with it — a symbiotic system.

### The coupling loop

```
User lives → generates experience
                ↓
            Capture System receives (6 logs)
                ↓
            Synthesis Pipeline processes (Notes → Opp/Dir)
                ↓
            Engines operationalize (Definition/Action/Context update)
                ↓
            LifeOS feeds back to User (insights, directives, stats)
                ↓
            User reflects + decides
                ↓
            User acts → generates new experience
                ↓
            (loop continues)
```

This is a **tight feedback loop** — the prosthetic becomes an extension of the user's cognition. The user doesn't "open LifeOS to check something" — they're continuously coupled, like a cyborg.

### Design criteria: efficiency, adaptability, efficacy

The user specified these as the criteria for the coupling:

**Efficiency** — minimal friction between user experience and LifeOS capture:
- 10-second logging (a log entry shouldn't take longer than the experience it captures)
- No mandatory ontology on capture (logs are objective; synthesis assigns meaning later)
- Quick-entry interfaces (voice, mobile, hotkey)

**Adaptability** — LifeOS reorganizes itself as the user's trajectory shifts:
- When the user's developmental level shifts, the engines reorganize (new Values, new goal structure, new context)
- When the user's circumstances shift (new city, new job, new relationship), Context Engine auto-updates
- When synthesis reveals a pattern, the engines adapt (new Directives spawn new Projects without user micromanagement)

**Efficacy** — the synthesis actually informs the user's decisions + identity:
- The morning view shows trajectory + progress + today's direction + accomplishments + stats (not just a task list)
- Insights surface proactively (not buried in a DB the user has to remember to check)
- Stats evolves as a living profile, not a static report

## The A+D Synthesis (how the 5 pillars map onto the 3 engines)

The user liked both A (3-Engine) and D (5-Pillar). Here's how they synthesize:

- **A's 3 engines** = the **operational layer** (how the system runs)
- **D's 5 pillars** = the **functional layer** (what the system does for the user)

The 5 pillars map onto the 3 engines + the 2 upstream systems:

| D's Pillar | Function | → A's location |
|------------|----------|----------------|
| **Mirror** | "How am I doing?" | Capture System (6 logs = granular mirror) + Definition Engine (Stats = aggregate mirror) |
| **Compass** | "Where am I going?" | Definition Engine (Values, Vision) + Action Engine (Annual/Quarterly Goals) |
| **Engine** | "What am I doing?" | Action Engine (Projects, Tasks, Campaigns, Content) |
| **Synthesizer** | "What does it mean?" | Synthesis Pipeline (Notes, Opportunities, Directives) |
| **Ecosystem** | "What's around me?" | Context Engine (People, Communities, Financial-Accounts) |

The pillars are the **user-facing questions**. The engines are the **operational processes** that answer them. The user asks "How am I doing?" (Mirror); the system answers by flowing through Capture (granular) → Synthesis → Definition Engine's Stats (aggregate).

## What This Architecture Gets Right (vs. the previous framings)

1. **Engines are processes, not containers.** The "operationalizes itself" correction means the engines live at the intersection of synthesis + trajectory. They can't die (go stale) as long as the flows continue.

2. **User is in the system, not outside it.** The coupling loop makes the user a system component, not an external user. This is what "consciousness-prosthetic" actually means.

3. **Capture is unified.** The 6 logs are one perception system with 6 channels. This matches the user's instruction + keeps capture frictionless (one mental model, not six).

4. **Synthesis is the bloodstream.** It's not a "stage" — it's the flow that keeps everything alive. Without it, the engines freeze.

5. **Trajectory is the spine.** The user's lived temporal arc is what the engines flow along. Without it, the engines have nothing to process.

6. **A+D synthesize cleanly.** The 5 pillars (user-facing functions) map onto the 3 engines + 2 upstream systems (Capture + Synthesis). No redundancy.

## Open Questions (for the user)

1. **Is the User System correctly characterized?** I have 3 components: Trajectory, Agency, Reflection. Is there a 4th? (e.g. "Embodiment" — the physical body that generates Activity/Diet logs? Or is that just part of Trajectory?)

2. **Where does Notes-Management sit?** Currently it's the "raw" stage of the Synthesis Pipeline. But Notes can also be Capture (web clips, voice memos, meeting notes). Is Notes-Management a capture channel AND a synthesis stage? Or should it be split?

3. **Stats as bridge.** Stats is the output of the Definition Engine (aggregate state) AND it feeds back to the User as self-understanding. Is Stats the primary interface between LifeOS and User? Or is that the Synthesis Pipeline's role?

4. **The coupling friction.** The user specified "maximum efficiency" — but the coupling loop has 6 steps (live → capture → synthesize → operationalize → feed back → reflect). Where's the friction likely to be highest? (My guess: capture friction — if logging takes >10 seconds, the loop breaks.)

5. **Engine autonomy.** "Operationalizes itself" suggests the engines have some autonomy — they update without the user micromanaging. How autonomous should they be? (e.g. Should Directives auto-spawn Projects, or always require user approval? Per AGENTS.md §6.1, the answer is "user approval" — but does that break the "operationalizes itself" property?)
